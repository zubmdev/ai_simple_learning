# День 1: Анатомия промпта — P.T.C.F. 🔬

**Трек:** 👨‍💻 Программист | **Время:** 25 минут

---

## 💡 Идея дня

Промпт для агента — это не просьба, а **спецификация задачи**: как тикет для сильного разработчика, у которого нет доступа к твоей голове. Половина P.T.C.F. — это критерии приёмки.

```
P - Persona (Роль)
T - Task (Задача + критерии приёмки)
C - Context (Контекст)
F - Format (Формат вывода)
```

---

## 📋 Структура

### 1️⃣ Persona (Роль)

```markdown
Ты — Senior Python разработчик с 10+ годами опыта.
Специализация: чистый код, тестирование, архитектура.
```

**Когда использовать:**
- Нужен специфический стиль кода
- Важны best practices
- Нужен педагогический подход

### 2️⃣ Task (Задача + критерии приёмки)

```markdown
Напиши функцию для валидации email:
- Проверка формата
- Обработка edge cases
- Return bool

Готово, когда:
- Пустая строка и None возвращают False, не бросают исключение
- Есть pytest-тесты минимум на 5 кейсов
- Тесты проходят локально
```

**Правила:**
- Задача конкретная, измеримая, однозначная
- Критерии приёмки — проверяемые утверждения, не пожелания
- «Сделай хорошо» — не критерий. «Тесты проходят» — критерий

### 3️⃣ Context (Контекст)

```markdown
- Это для production API регистрации
- High-load: миллионы запросов/день
- Python 3.10+, стандартная библиотека
- Файлы: src/validation.py (туда), tests/test_validation.py (тесты туда)
```

Агент в Cline сам читает файлы проекта — указывай пути, а не вставляй весь код.

### 4️⃣ Format (Формат)

```markdown
- Type hints для всех аргументов
- Docstring в Google формате
- Diff до применения, затем объяснение правок
- Без внешних зависимостей
```

---

## 🛠️ Пример: полный промпт-спека

```markdown
## Persona
Ты — Senior Python разработчик, специализируешься на data validation.

## Task
Напиши функцию validate_email(email: str) -> bool

## Context
- Production API регистрации пользователей
- High-load: миллионы запросов/день
- Python 3.10+, только стандартная библиотека
- Отсеять явно невалидные email

## Готово, когда
- Невалидные входы возвращают False, а не бросают исключения
- Есть pytest-тесты: валидный, пустой, None, без @, двойной @
- Все тесты проходят: pytest tests/test_validation.py

## Format
- Type hints, Google docstring с 3-5 примерами
- Сначала diff, потом краткое объяснение правок
```

---

## 📊 Сравнение: просьба vs спецификация

| Просьба (плохо) | Спецификация (хорошо) |
|-----------------|----------------------|
| "Напиши функцию" | "Напиши функцию X. Готово, когда тесты A/B/C проходят" |
| "Сделай что-то с базой" | "Напиши PostgreSQL query для таблицы users. Готово, когда EXPLAIN не показывает seq scan" |
| "Исправь ошибку" | "Ошибка X в src/foo.py:42. Готово, когда тест, воспроизводящий баг, проходит" |

Разница: у спецификации есть проверяемое «готово». У просьбы — только мнение агента о себе.

## 🛠️ Практика (10 минут)

Возьми спеку из миссии Дня 1 Недели 1 и прогони её через агента в Cline:

1. Отправь спеку с секцией «Готово, когда»
2. Получи дифф — сделай ревью
3. Запусти тесты из критериев приёмки

Затем сравни: отправь ту же задачу без критериев («напиши функцию валидации email») и посмотри на разницу в результате.

## 🎯 Миссия

Напиши полную промпт-спеку (P.T.C.F. + критерии приёмки) для одной функции из твоего реального проекта и прогони через агента.

**Формат артефакта:** текст спеки (4 секции, минимум 3 критерия приёмки) + применённый дифф.

**Проверка:** агентский результат проходит каждый критерий приёмки; если хоть один не проходит — спека дорабатывается и цикл повторяется.
