## 🚨 Проблема: просьба без критерия

### Плохая просьба

```text
Напиши функцию сортировки
```

**Что не так:**
- ❌ Не указан язык и что сортировать
- ❌ Не описаны требования к результату
- ❌ Главное: непонятно, **как проверить**, что результат правильный

**Результат:** модель напишет что-то правдоподобное. Подошло оно или нет — неизвестно.

### Спецификация

```text
Напиши функцию sort_numbers(numbers: list[float]) -> list[float] на Python.

Требования:
1. Быстрая сортировка (quicksort)
2. Пустой список возвращает пустой список
3. Docstring в формате Google
4. Работает с дубликатами

Критерий приёмки — скрипт check_sort.py проходит без ошибок:
- sort_numbers([3, 1, 2]) == [1, 2, 3]
- sort_numbers([]) == []
- sort_numbers([2, 2, 1]) == [1, 2, 2]
```

**Результат:** и задача, и способ её принять описаны заранее. Спорить не о чем — запускай проверку.

## 💡 Пять компонентов промпта-спецификации

**Аналогия:** заказ у подрядчика. «Сделайте красиво» — просьба. Спецификация — это чертёж, материалы и пункт приёмки: «дверь открывается, замок работает». Промпт устроен так же.

| Компонент | Вопрос | Пример |
|-----------|--------|--------|
| 1️⃣ Роль | Кем будет модель? | «Ты — Senior Python-разработчик» |
| 2️⃣ Задача | Что конкретно сделать? | «Напиши функцию validate_email» |
| 3️⃣ Контекст | Что модель должна знать? | «Учебный проект, код читают новички» |
| 4️⃣ Ограничения | Каких правил придерживаться? | «Только стандартная библиотека» |
| 5️⃣ Критерий приёмки | Как принять или отклонить результат? | «check.py печатает OK» |

Первые четыре компонента описывают **что делать**, пятый — **как понять, что сделано**. Без пятого это не спецификация, а всё ещё просьба.

### Критерий приёмки: каким он бывает

| Вид | Пример | Как проверять |
|-----|--------|---------------|
| Запускаемый скрипт | «все assert-ы проходят» | `python check.py` |
| Сравнение вывода | «программа печатает 80.0» | запуск и взгляд на вывод |
| Форма результата | «JSON с ключами valid и reasons» | парсинг + проверка ключей |
| Чеклист формы кода | «type hints, docstring, timeout» | просмотр диффа по чеклисту |

Правило: критерий должен решать спор **без вкусовщины**. «Код хороший» — не критерий. «Тесты зелёные» — критерий.

## 🛠️ Практика: спецификация для валидатора email

Работаем в VS Code с Cline (настройка — в Неделе 1). Модель — по твоему железу:

| Уровень | Агент | Модель |
|---------|-------|--------|
| CPU + бесплатный API | Cline + Groq | `openai/gpt-oss-20b` |
| 4GB GPU | Cline + Ollama | `qwen3.5:2b` |
| 16GB GPU | Cline + Ollama | `gpt-oss:20b` |

*Проверено: 2026-10-24*

### Шаг 1: Определи компоненты

- **Роль:** Senior Python-разработчик, валидация данных
- **Задача:** функция `validate_email(email: str) -> bool` в файле `validate_email.py`
- **Контекст:** проверка при регистрации, отсеять явно некорректные адреса
- **Ограничения:** только стандартная библиотека, без исключений
- **Критерий приёмки:** скрипт проверок проходит

### Шаг 2: Подготовь проверку заранее

Проверка пишется **до** кода — так же, как критерии в ТЗ пишутся до работы. Сохрани `check_email.py`:

```python
from validate_email import validate_email

cases = {
    "user@example.com": True,
    "ok.user@site.org": True,
    "invalid-email": False,
    "user @example.com": False,
    "a@b": False,
}

for value, expected in cases.items():
    got = validate_email(value)
    assert got == expected, f"{value!r}: ожидали {expected}, получили {got}"

print("Все проверки пройдены")
```

### Шаг 3: Напиши спецификацию

```text
Ты — Senior Python-разработчик, специализирующийся на валидации данных.

Задача: напиши функцию validate_email(email: str) -> bool в файле validate_email.py.

Контекст: функция используется при регистрации пользователей; нужно отсеять
явно некорректные email (без @, без домена после @, пробелы, короче 5 символов).

Ограничения:
- только стандартная библиотека (модуль re)
- не выбрасывай исключения, только return True/False
- docstring в формате Google

Критерий приёмки: check_email.py (код ниже) должен напечатать «Все проверки пройдены».
[вставь содержимое check_email.py]
```

### Шаг 4: Делегируй и проверь

1. Отправь спецификацию в Cline.
2. Перед сохранением посмотри дифф: те ли файлы тронуты, нет ли лишних изменений.
3. Запусти проверку:

```text
python check_email.py
```

Ожидаемый вывод:

```text
Все проверки пройдены
```

4. Если проверка упала — не правь код руками. Верни агенту факт:

```text
Проверка не прошла: "a@b" — ожидали False, получили True.
Трогай только validate_email.py, затем покажи дифф.
```

Повторяй цикл «дифф → проверка → уточнение», пока проверка не станет зелёной. Это и есть работа с агентом, а не угадывание.
